Connect Claude to TradingView on Windows

Most write-ups of this setup are Mac-only — they assume Homebrew paths and macOS scheduling. This is the Windows version: the PowerShell install, the debug-port workaround for Microsoft Store installs of TradingView, Task Scheduler instead of launchd, and the PowerShell fix for Telegram alerts.

🪟 Windows 10 / 11 ⏱️ ~45 min setup 🧩 Third-party tool — not an Arowana feature 📅 Updated September 2026
Read this first This guide documents a free, open-source community tool that bridges Claude Code and TradingView Desktop. It is not built, maintained, or supported by Arowana Profits, and it relies on an undocumented debug interface inside TradingView's desktop app — meaning a TradingView update can break it without warning. We publish it because our users keep asking. If something here stops working, the tool's GitHub issue tracker is the right place to go, not our support inbox.

What this actually builds

TradingView Desktop is an Electron app, which means it exposes the same Chrome DevTools Protocol (CDP) debug interface that VS Code, Slack, and Discord do. An open-source MCP server — built by @tradesdontlie — connects to that interface on your own machine and gives an AI agent the ability to read and drive your charts. Wire it to Claude Code and you can ask, in plain English, for things like:

  • Switch the chart to a symbol and timeframe, and add indicators
  • Read your watchlist and rank what's moving
  • Pull OHLCV data and compute levels — premarket high, prior-day high, a 200 SMA
  • Write, compile, and backtest a PineScript strategy, then read the Strategy Tester results back
  • Run all of the above on a schedule and text you the output

The workflow below is adapted for Windows from Shay's original Mac walkthrough at Humbled Trader, whose FAQ notes the scheduling layer is the only genuinely Mac-specific piece. That's accurate — and it's the part we've rewritten below.

Before you start

Install these first — every step below assumes them:

  • Node.js — the MCP server is a Node app and you'll run npm install.
  • Git for Windows — needed to clone the repo. It also gives Claude Code its Bash tool. Without it Claude Code falls back to PowerShell as its shell, which works fine, but you'll want your automation scripts written as .ps1 instead of .sh.
  • A paid Claude plan. Claude Code has no free tier. Pro is enough to follow this guide by hand.
  • A paid TradingView plan. The entry tier covers the scanner workflow; PineScript backtesting with bar replay needs a higher tier.

Step 1 — Install Claude Code

Windows PowerShell

Open PowerShell (press Win, type "PowerShell", hit Enter) and run:

irm https://claude.ai/install.ps1 | iex

Prefer a package manager? WinGet works too, though it won't auto-update:

winget install Anthropic.ClaudeCode
Close and reopen your terminal before continuing. The installer adds itself to your PATH, and Windows doesn't push that change into terminal windows that are already open. Skipping this is the number-one reason people see "command not found" here.

In a fresh window, confirm it worked:

claude --version

You should get a version number back. If not, run claude doctor for diagnostics.

Step 2 — Install TradingView Desktop

Download the desktop app from your TradingView account page and sign in. The browser version will not work — the bridge talks to the Electron app on your machine, and there's no equivalent hook in a browser tab.

Open a chart on any symbol and leave it there. A blank "New Tab" welcome screen doesn't count; the tools need a live chart to read.

Step 3 — Install the TradingView MCP

This is the bridge. Installation takes two prompts with a Claude Code restart between them — the restart is what loads the new server into your session.

Prompt 1 — paste into Claude Code 
Install the TradingView MCP server from https://github.com/tradesdontlie/tradingview-mcp

I'm on Windows. Clone it to %USERPROFILE%\tradingview-mcp, run npm install, and register
it in my Claude Code MCP config at user scope. Then launch TradingView Desktop with the
remote debugging port enabled on port 9222 — use the tv_launch tool if it's available,
otherwise detect whether my install is a Microsoft Store (MSIX) install or a legacy install
and use the correct launch method for that. Tell me when you're done.

Claude will ask permission before each shell command — the clone, the npm install, the config write, and the TradingView launch. Approve each one.

Now quit Claude Code (Ctrl+C or close the window) and relaunch it. In the new session:

Prompt 2 — paste into the new session 
Run tv_health_check and tell me if TradingView is connected.

You're looking for cdp_connected: true and api_available: true. If you get those, the hard part is done.

Step 3b — The Windows debug-port problem

This is where Windows genuinely differs, so it's worth understanding rather than just pasting. TradingView must be launched with the --remote-debugging-port=9222 flag. Nothing happens without that flag — the port is off by default.

The complication: TradingView's Windows desktop app now ships as an MSIX (Microsoft Store) package, installed under C:\Program Files\WindowsApps. Launching an executable directly from that folder with custom arguments throws Access is denied.

If you have a legacy (pre-MSIX) install

%LOCALAPPDATA%\TradingView\TradingView.exe --remote-debugging-port=9222

If you have the Microsoft Store / MSIX install

The documented workaround is to copy the package out to a normal folder and run the copy. Reading files out of WindowsApps by exact path is permitted even where executing them isn't: 

$pkg = (Get-AppxPackage TradingView.Desktop).InstallLocation
Copy-Item "$pkg\*" "$env:LOCALAPPDATA\tradingview-mcp\TradingView" -Recurse -Force
& "$env:LOCALAPPDATA\tradingview-mcp\TradingView\TradingView.exe" --remote-debugging-port=9222
Do not run icacls against WindowsApps. It's the first "fix" search results will suggest for the access-denied error. It doesn't work, and it can break Windows app servicing on your machine. Use the copy approach above instead.

Simplest path of all: once the MCP is connected, just ask Claude to run the tv_launch tool. It auto-detects your install location, MSIX included, and handles the fallback for you.

Step 4 — Try a few basic prompts

Before automating anything, get a feel for what the bridge can reach. Open your watchlist panel in TradingView first, then try these one at a time:

Switch the chart to NVDA on a 5-minute timeframe and add the 200 SMA and RSI.

Read my TradingView watchlist and tell me which names are up the most today.

Look at NVDA on the daily. Mark the support and resistance levels you consider
most important, plus today's premarket high.

Give me an end-of-day briefing on NVDA: what happened, which levels held or broke,
and what to watch tomorrow.

If all four work, the connection is solid and you can move on to the real workflow.

Step 5 — Build a premarket gap scanner

This one doesn't touch TradingView at all — it fetches public gainer data and news, filters it, and saves a JSON file. It's the foundation: candidates in, junk out, with a catalyst attached to each name so you can decide in seconds whether it's worth charting.

Prompt — Scanner A 
Build me a premarket gappers scanner as a single PowerShell script (.ps1) in this directory.
I'm on Windows — no bash, and use Invoke-RestMethod / Invoke-WebRequest rather than curl.

DATA SOURCE: fetch the public Yahoo Finance stock gainers page and parse out
ticker, price, gap %, and volume for each row.

FILTERS:
- gap_pct greater than 5
- price above $3
- premarket_volume above 50000
- keep the top 10 by gap_pct descending

NEWS CATALYST: for each of the top 10, fetch the Benzinga quote page for that ticker
and extract a one-sentence summary of what's driving the move, plus up to 2 recent
headlines. Data only, no commentary. If a single ticker's lookup fails, set catalyst
to null and headlines to an empty array for that ticker — do not abort the whole scan.

OUTPUT: save to .\premarket_gappers_YYYY-MM-DD.json with this schema:
{
  "scanned_at": "",
  "gappers": [
    {"rank": 1, "symbol": "AAPL", "price": 175.20, "gap_pct": 7.5,
     "premarket_volume": 1200000, "catalyst": "Beat Q1 earnings, raised guidance",
     "headlines": ["...", "..."]}
  ]
}

After saving, print a one-line summary naming the top 3 with their gap % and catalyst.
Expected runtime 60-90 seconds. Do not run it more than once unless I ask.
Tune the volume filter to your account size. 50,000 shares is a reasonable default. Drop to 20,000 for a wider net, raise above 100,000 if you trade size and need the liquidity. Names below your threshold will show up with spreads you can't trade around.

Step 6 — Schedule it with Task Scheduler

Here's the piece Mac guides can't help you with. macOS uses launchd; Windows uses Task Scheduler, and for this particular job Windows actually handles the sleeping-laptop case more gracefully.

Prompt 
This works. Now I don't want to run it manually every morning.

Schedule it with Windows Task Scheduler to fire every weekday at 8:30am New York time.
My laptop is sometimes asleep then. Don't wake the machine — instead enable "run task as
soon as possible after a scheduled start is missed" so it catches up when I open the
laptop, but add a guard so it won't run if it's already past market close.

Skip weekends, never run twice in the same day, and skip if the premarket data on disk
is already current. Register it with Register-ScheduledTask and show me the exact command
you used so I can inspect the task myself.

Verify the task registered:

Get-ScheduledTask | Where-Object TaskName -like "*premarket*"
Windows equivalents, if you're translating a Mac guide yourself: launchd → Task Scheduler · launchctl list → Get-ScheduledTask · open -a AppName --args → the executable path plus arguments · ~/ → %USERPROFILE%\

Step 7 — Build a strategy scanner

The gap scanner gives you candidates. A strategy scanner tells you which of them actually meet your entry criteria right now. This one does use the TradingView bridge, so the desktop app has to be running with the debug port live.

The example below encodes a trend-continuation long: a name trading above its prior-day high with the prior close above the 200 SMA, that has also broken above both the premarket high and the intraday high. Swap the criteria for your own setup — the structure stays the same.

Prompt — Scanner B 
Build me a trend-continuation long scanner that filters tickers down to which ones meet
my entry criteria right now. Write it as a PowerShell script.

TEST UNIVERSE: 3 tickers — AMD, NVDA, MU. Keep it small so the first run finishes quickly.

PREREQ: TradingView Desktop must be running with CDP port 9222 enabled. First call
tv_health_check. If cdp_connected or api_available is false, launch TradingView in debug
mode using tv_launch, then re-check. If it still fails, stop and tell me — don't proceed.

TIME GATE: only proceed between 10:00am and 3:30pm New York time. Otherwise write an
error JSON and exit cleanly.

FOR EACH TICKER, sequentially (do not parallelize):
1. chart_set_symbol to the bare ticker
2. chart_set_timeframe to "D", then data_get_ohlcv count=210 and compute:
   prev_daily_high, prev_daily_close, and sma200 (mean close of the last 200 bars)
3. quote_get for the current intraday price
4. chart_set_timeframe to "1", then data_get_ohlcv count=400 and compute:
   pmh  = highest high between 04:00 and 09:30 ET today
   hod  = highest high from 09:30 ET to now, excluding the current forming bar
5. Evaluate:
   daily_ok    = current price above prev_daily_high AND prev_daily_close above sma200
   intraday_ok = current price above pmh AND above hod
   result = PASS if both, otherwise fail_daily or fail_intraday

OUTPUT: save to .\strategy_watchlist_YYYY-MM-DD_HHMMET.json with scanned_at,
candidates_checked, a hits array with the computed levels, and an all_results array.

Then print one line per ticker: TICKER: PASS | fail_daily | fail_intraday — reason.
This one is slow by design. Each ticker takes several minutes — the agent loads the chart, pulls two timeframes of data, and computes the levels, one symbol at a time. A ten-name list is a half-hour of waiting. That's exactly why you schedule it rather than babysit it.

Schedule it for the rest of the session

A single 10am snapshot misses setups that develop at 10:45, 11:30, or after lunch:

Run this strategy scanner every 30 minutes from 10am to 2pm New York time via Task Scheduler.

Before each run, check tv_health_check — if TradingView isn't up with the debug port,
launch it with tv_launch first, then proceed.

Don't blow up my phone with 9 messages a day. Only notify me on the first run of the day,
when there's a new hit that wasn't in the previous run, or on error. Otherwise stay quiet.

Step 8 — Backtest it in PineScript

The obvious next question is whether the setup makes money. Claude can write the PineScript, inject it into TradingView's Pine editor, compile it, apply it to the chart, and read the Strategy Tester numbers back.

Prompt 
Build a backtest of my trend-continuation long strategy in TradingView, end to end:

1. Call tv_health_check and confirm the connection. If it fails, launch TradingView with
   tv_launch and retry.
2. chart_set_symbol("AMD"), chart_set_timeframe("5"), and confirm Extended Hours is enabled —
   the strategy needs premarket bars to compute the premarket high.
3. Open the existing Pine slot named "Demo Strategy" with pine_open using that exact name.
   Do NOT use pine_new — I don't want other Pine slots overwritten.
4. Write the strategy in Pine v5 implementing the same entry rules as my scanner, inject it
   with pine_set_source, then pine_smart_compile. If has_errors is true, show me the error
   and stop — don't auto-fix without telling me what changed.
5. Once it compiles clean, find the "Add to chart" button and click it to apply the strategy.
6. Read the Strategy Tester results. If the results tool returns empty, screenshot the
   Strategy Tester panel and read the numbers off the image instead.
7. Report win rate, total trades, total P&L, profit factor, and max drawdown.
Expect two or three compile cycles. Pine is picky about types. Claude will write, hit a syntax error, read the error back from TradingView, fix it, and recompile. That loop is normal — let it run rather than interrupting mid-fix.

Then test your assumptions, not just your strategy

The most valuable thing this setup buys you isn't the scanner — it's how cheap it becomes to test an idea you'd otherwise just believe. A worked example: most traders assume a momentum long works better when SPY and QQQ are also green, so they'd add that filter without testing it. 

Test whether adding an SPY/QQQ regime filter improves this strategy. Modify the SAME
"Demo Strategy" Pine slot — add the filter on top of the existing entry logic, don't
rewrite the strategy — then re-run and compare against the numbers you just gave me.

REGIME FILTER: at the first 5-minute bar at or after 10:00am ET each day, latch a flag
that is true only if SPY's current close is above its previous daily close AND QQQ's
current close is above its previous daily close. Use request.security with
lookahead=barmerge.lookahead_off. Hold the flag for the rest of the day, reset on a new
day, and require it as an additional entry condition. Tint the background faintly red on
days the filter gates us out so it's visible.

Report back a table comparing total trades, win rate, total P&L, and profit factor with
and without the filter — then tell me in plain English whether it helped or hurt, and
whether the difference is large enough to change how I trade.

When Shay ran this test, the "obvious" filter hurt — meaningfully. The reasoning holds up: a momentum name breaking out on a red-tape day is showing relative strength, which is the exact condition you want, and the filter throws those trades away. Worth running yourself on your own universe before you trust either result. Test the obvious stuff.

Step 9 — Send alerts to your phone

Telegram is the least-friction option — no business verification, no SMS carrier, free.

  1. In Telegram, message @BotFather, send /newbot, and copy the token it gives you.
  2. Open the t.me/ link BotFather returns and send /start so the bot is allowed to message you.
  3. Visit https://api.telegram.org/bot<YOUR_TOKEN>/getUpdates in a browser and find the "chat":{"id": value. That number is your chat ID.
Your bot token is a password. Anyone holding it can send messages as your bot. Keep it in a .env file or a password manager — never in a shared chat, a screenshot, or a committed file.
Prompt 
Wire up Telegram notifications for both scanners. I'm on Windows.

CREDENTIALS: my bot token and chat ID are in .env in this directory as TELEGRAM_BOT_TOKEN
and TELEGRAM_CHAT_ID. Read them at runtime. Never print the token to stdout or write it
into any file.

IMPORTANT: in PowerShell, curl is an alias for Invoke-WebRequest and will not accept curl
flags. Use Invoke-RestMethod against the Telegram sendMessage endpoint instead, posting
chat_id, text, and parse_mode=Markdown as the body.

Modify both scanner scripts to send a message after saving their JSON:
- Gap scanner: a dated header, then one bullet per name with ticker, price, gap %, and
  catalyst. Omit the catalyst portion when it's null.
- Strategy scanner: a header with the time in ET, then one bullet per hit with ticker,
  price, and the computed levels. If there are no hits, say so in one line.

GATING: send the gap scanner result on every run. Send the strategy scanner only on the
first run of the day, on a new hit, or on error. If a send fails, log it but don't fail
the scan.

Then run the gap scanner once so I can confirm the message lands on my phone.

Email, Discord, and Slack all follow the same pattern — give Claude the credentials and the format, and it wires the rest. WhatsApp is the exception: it needs the Business API, Meta verification, and a paid carrier. Not worth it unless you have a specific reason.

Step 10 — Stop here, for now

The natural next step is connecting a broker so the agent can place orders. Before you go there: forward-test on a paper account for at least a month, and build the safety layer first — position sizing caps, a daily loss limit that halts trading, and a hard stop on order size. An automation bug with live buying power is a different category of problem from a scanner that returns bad data.

Never point this at a live account you haven't paper-traded for a month. If something goes wrong — and with an unofficial interface, something eventually will — you want it to cost you pretend money.

Troubleshooting

SymptomFix
claude not recognized after install Close and reopen your terminal. The PATH change doesn't reach already-open windows. Then try claude doctor.
'irm' is not recognized You're in CMD, not PowerShell. Your prompt shows PS C:\ in PowerShell. Use the CMD installer variant or open PowerShell.
cdp_connected: false TradingView isn't running with --remote-debugging-port=9222. Quit it completely first — a background instance without the flag will block the relaunch — then use tv_launch.
"Access is denied" launching TradingView MSIX/Store install. Use the copy-to-LOCALAPPDATA snippet in Step 3b. Do not use icacls on WindowsApps.
ECONNREFUSED TradingView isn't running, or port 9222 is taken. Ask Claude to move both the MCP config and the launch flag to 9223.
MCP server doesn't appear in Claude Code Check your MCP config file for a JSON syntax error, then fully restart Claude Code — servers load only at startup.
Tools return stale or empty data TradingView may still be loading. Give it a few seconds and make sure a real chart tab is open, not the welcome screen.
Pine editor tools fail Open the Pine Editor panel in TradingView first, then retry.
Scheduled task never fires Check that the task is registered with Get-ScheduledTask, and that its "run whether user is logged on or not" and missed-start settings match what you asked for.

FAQ

Do I need to know how to code?

No. Every prompt here is plain English and Claude writes the code. You do need to be comfortable pasting commands into PowerShell and approving permission prompts. If that sentence makes you uneasy, this isn't the right project for you.

Does this place trades?

No. Reading and analysis only. Order execution requires a separate broker integration, which is a much bigger safety problem and shouldn't be attempted until the read-only layer has been stable for a while.

Is my data safe?

The bridge runs locally — it talks to TradingView Desktop on your own machine over a local port. Your TradingView credentials are never sent to Claude or Anthropic.

One thing to be clear about: anything the AI reasons over — chart data, your levels, your strategy code — is sent to Anthropic's API, the same as any Claude conversation. That's how the model works at all. If you have signals you don't want passing through a cloud model, that matters.

Will TradingView updates break this?

Likely, eventually. The bridge uses an internal debug interface, not a supported public API. If stability matters more than new features to you, pin your TradingView Desktop version once the setup is working.

Is this allowed under TradingView's terms?

Reading your own paid TradingView Desktop app on your own machine for personal use is doing automatically what you'd otherwise do by hand. What is clearly not allowed: redistributing the data, running a paid signals service off it, or accessing data your plan doesn't cover. TradingView's terms restrict automated collection and non-display usage.

If you plan to build anything commercial on top of this, read the terms yourself or contact TradingView directly. Nothing here is legal advice.

What does the whole stack cost?

To follow this guide and run scanners by hand: entry-tier TradingView plus Claude Pro, roughly $33/month.

To run it automated all session: the strategy scanner firing every 30 minutes will exhaust a Pro plan's usage before lunch, so you're looking at Claude Max, putting the stack near $113/month. Deep multi-year PineScript backtesting pushes the TradingView tier up as well.

The MCP server itself is free and open source.

Can I use a different AI model?

You need a coding agent that runs locally and speaks MCP. Consumer chat apps in a browser can't reach a local MCP server. Other CLI coding agents support MCP and could plausibly run a similar setup, though the prompts here were written against Claude Code.

No. We publish it as education because our users ask about it, but it's a third-party open-source tool and we can't troubleshoot it. Issues belong on the project's GitHub tracker. Our support covers Arowana Pro Desk only.
