## Scope and replay prerequisites

The SQL recreates only the listed `public` and `arowana` relations, the enum they use, and relevant RPC/trigger/policy helper functions. `profiles`, `business_profiles` and several finance relations are shared objects explicitly named in the handoff; their existing columns and policies are preserved. For example, the existing business-profile policy references `salon.employees`. No Salon/Rental tables or schemas are created, altered or copied.

The migration is intentionally NOT a standalone empty-project bootstrap. It checks for external relation dependencies first and refuses to overwrite any of the 33 existing target relations. Required external relations are:

- `auth.users` (Supabase-managed);
- `public.companies`, `public.finance_categories`, `public.agent_memberships`, `public.entity_memberships`, `public.gs_user_preferences` (shared dependencies outside the table allowlist);
- `arowana.tools`, `arowana.webhooks` (backing relations outside the handoff table list);
- `public.ap_admins`, `public.ap_provider_calls`, `public.journal_trade_candidates` (dependencies of captured Arowana RPCs);
- `salon.employees` (referenced by an existing policy on the explicitly included shared `business_profiles` table).

It also requires Supabase roles/Auth functions and `uuid_generate_v4()` (uuid-ossp visible through `public, extensions`). If the shared `public.finance_direction` enum exists, its labels must match the capture. No external dependency is fabricated or silently dropped. Capture/replay of those dependencies requires a separate scoped follow-up. Runtime function dependencies also include `ap_email_prefs`, `ap_email_log` and `arowana_digest_cron_secret`; these are outside the handoff table list and are not a claim of a complete runnable email backend. Wheel cron migrations were not copied, and no cron secret function was invoked.

Defaults, constraints, RLS flags, permissive/restrictive policy behavior, view security-invoker options, trigger states, owners and privileges are retained. The baseline restores exact observed grants after revoking standard-role defaults on the new objects. It does not repair pre-existing broad policies or ownership weaknesses. `ap_claim_usage` and `ap_add_usage_cost` retain EXECUTE only for postgres and service_role.
